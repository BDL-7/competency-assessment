Your understanding is mostly correct: **a model service requires more application work than a ready-made bot, but you do not build or train the AI model.** Also, direct OpenAI API access is itself a form of model service; it can include hosted retrieval tools.

These are **design recommendations**, not changes to the approved architecture. EDAV’s preference for Word/PDF comes from your reported guidance.

| Approach | What the provider supplies | What we build or configure | Knowledge formats | Buildathon fit |
|---|---|---|---|---|
| **EDAV Bot as a Service / Microbot** | A managed bot experience and its configured retrieval capabilities; exact features depend on EDAV | Approved content, bot instructions, answer checks, and application embedding/authentication where available | **Word/PDF**, following EDAV’s guidance; export approved Excel reference data into readable documents | **Least development work if provisioned.** Your prior iframe difficulties make integration the main schedule risk. |
| **EDAV Model as a Service** | Access to a hosted model endpoint; additional tools depend on the service | Chat interface, backend calls, source selection/retrieval, citations, access checks, errors, and evaluation | **Markdown/text** for context; parsed Word/PDF; controlled SQL results | **More work, more control.** Attractive if an approved working endpoint is available but Microbot is blocked. |
| **Direct OpenAI API with hosted file search** | Model access plus managed file search | Chat/backend integration, file uploads, source permissions, citation display, evaluation, and any SQL tools | Hosted file search supports **DOCX, PDF, Markdown**, among other formats | **Moderate work if already authorized and accessible.** A new provider approval could outweigh coding speed. |
| **Model API with fully custom retrieval** | Model inference | Document extraction, indexing, search, ranking, SQL tools, source filtering, citations, chat, and operations | Documents plus structured database results | **Most work.** I would avoid this for the buildathon unless existing components already solve it. |

OpenAI’s hosted file search performs semantic and keyword retrieval over uploaded files, so direct API use does **not** necessarily mean building your own search engine. That capability should not be assumed available through EDAV’s endpoint. [Official OpenAI documentation](https://developers.openai.com/api/docs/guides/tools-file-search)

**For accuracy, the important buildathon shortcut is reducing integration—not relaxing source controls.** Use one approved document set accessible to the intended demonstration audience, preserve catalog relationships when exporting, label snapshot dates, and check answers against their supporting passages. A manifest or prompt alone cannot enforce document permissions.

**My choice would be BaaS if the bot is available; an approved EDAV model endpoint if embedding is a hard requirement and BaaS integration remains blocked.** I would keep direct OpenAI access as an alternative requiring explicit platform approval, and avoid building a custom retrieval system for this event.
