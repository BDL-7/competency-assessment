Provisioning Approaches Compared

Approach Details
EDAV BaaS (Bot as a Service) / Microbot
  • What the provider gives us: A ready-made bot and its built-in search features. Exactly what it can do depends on EDAV.
  • What we set up: The approved content, the bot's instructions, answer checks, and (where possible) embedding it in our app with login.
  • Knowledge formats: Word/PDF, per EDAV's guidance. Turn approved Excel data into readable documents.
  • Short-term fit: Least work to build, if we get access in time. Past trouble embedding it (iframe issues) is the main schedule risk.
  • How embedding works: The bot loads inside our page in an iframe (a framed window-within-a-page), and the two communicate through postMessage, the browser's secure way to pass data between a page and an embedded frame.
EDAV MaaS (Model as a Service)
  • What the provider gives us: Access to a hosted model. Any extra tools depend on the service.
  • What we set up: The chat screen, backend calls, picking and fetching sources, citations, access checks, error handling, and testing.
  • Knowledge formats: Markdown/text as context, plus Word/PDF we parse and controlled SQL results.
  • Short-term fit: More work, but more control. A good fit if we have a working endpoint but can't use Microbot.
Direct OpenAI API with hosted file search
  • What the provider gives us: Model access plus a built-in file search.
  • What we set up: The chat and backend, file uploads, source permissions, showing citations, testing, and any SQL tools.
  • Knowledge formats: The built-in file search handles DOCX, PDF, Markdown, and more.
  • Short-term fit: Moderate work if we're already approved to use it. Getting a new provider approved could cost more time than it saves.
Model API with fully custom retrieval
  • What the provider gives us: Just the model itself.
  • What we set up: Everything — reading documents, indexing, search, ranking, SQL tools, source filtering, citations, chat, and upkeep.
  • Knowledge formats: Documents plus structured database data.
  • Short-term fit: The most work. Skip it for the short term unless we already have the pieces built.
In the table below, "Ideal" means the recommended long-term design. "Short-term" means the faster, lighter version (such as for the buildathon), using versioned reference snapshots rather than live database integration.
